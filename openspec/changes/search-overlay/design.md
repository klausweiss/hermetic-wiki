# Design

## Context

`<hermetic-search>` (`static/packages/search/src/elements.ts`) sits in the header's `<nav>`. When the script runs over `http(s)`, it renders a `<form>` with a 12rem input and an absolutely positioned `.search-dropdown` listbox. The shortcuts element focuses it through the `SEARCH_FOCUS` event (`/`, and `Ctrl+K` even while typing). It detects search through `hermetic-search input`. The editor inserts its status before `<hermetic-search>` in the nav. The results rendering (`renderResult`, `note`, `find`), the debounce, and the keyboard selection all stay. Only where they live changes. See proposal.md for why.

## Goals / Non-Goals

**Goals:**
- No search markup change from Rust: the same `<hermetic-search>` element renders a button and a dialog.
- Reuse the existing result list and keyboard handling unchanged inside the dialog.

**Non-Goals:**
- Changing ranking, the index, or `search.html`'s full results list.
- Searching anything other than the site index (no commands, no graph nodes).
- Footer content beyond the all-pages link, "Generated by hermetic", the commit, and the project link (no date: output must stay deterministic).

## Decisions

### A modal `<dialog>` inside `<hermetic-search>`
`showModal()` puts the dialog in the top layer wherever it sits in the DOM. It makes the rest of the page inert, so keyboard focus can't leave the dialog, and it fires `cancel` on Escape. That gives the focus behavior the spec asks for without a hand-written focus trap. The alternative, a positioned `<div>` plus an overlay, would need all of that written by hand. The dialog has no padding of its own and holds a `.search-panel`, so a click whose target is the dialog itself is a click on the backdrop and closes it. The previously focused element is remembered when the dialog opens and focused again on `close`; recent browsers do this on their own, but not all versions do.

### Opening, closing, toggling
- The header button and `/` open the dialog through `SEARCH_FOCUS`, as today.
- `Ctrl+K` toggles it through a new `SEARCH_TOGGLE` event in `@hermetic/core`. The shortcuts element keeps handling the key, also while typing, so the input in the dialog closes it too.
- Opening selects the field's text. On `search.html` the field starts with `?q=`, as the input does today.
- Escape closes the whole dialog. Previously, the first Escape only hid the results. In a modal there is nothing behind the results to go back to.

### Layout
`dialog.search-dialog`: `width: min(40rem, calc(100vw - 16px))`, top margin about 12vh (0.5rem below 600px wide), `max-height: 76vh`. The result list scrolls inside it. The old `.search-dropdown` positioning and the narrow-screen rule that made `hermetic-search` a full-width row are removed. The list stays a `role="listbox"` controlled by the input. The header button uses the same button style and icon size as the other script-added icon buttons. Its accessible name is "Search (/ or Ctrl+K)", or ⌘K on Apple platforms.

### Interplay with other keys
- `shortcuts.hasSearch()` looks for the search button instead of the input.
- `?` and `g …` are already ignored while typing, so they don't fire inside the dialog.
- The graph's `Ctrl+F` listener leaves the key alone while any modal dialog is open (`dialog[open]:modal`), so the graph search never opens behind the search dialog.

### Site footer inside `<hermetic-sidebar>`
`html::document` writes `<footer class="site-footer">` with the all-pages link and "Generated by hermetic" as the child of `<hermetic-sidebar>`. Without the script, the element is an unknown inline element whose children render normally, right after `<main>`, so the footer is a plain page footer. On setup, the sidebar moves it into its `<aside>` after the pane list. The aside is a column whose pane list scrolls, so the footer stays at the bottom. The alternative, the script creating the footer, would leave pages without JavaScript with no link to the all-pages list at all. The footer is not part of `<main>`, so sidebar panes (which show the fetched `main > article`) never include it.

### Commit hash at compile time
A build script, `src/build.rs` (named by `build` in Cargo.toml, so the root holds no extra file), runs `git rev-parse --short=7 HEAD` in the crate's directory and passes the result as `HERMETIC_COMMIT`. When git or the repository is missing (a source archive), the variable is empty and the footer leaves the commit out. It reruns when `.git/HEAD` or the refs change. Builds by the same binary therefore stay byte-identical. Installing with `uv tool install git+ssh://…` builds from a git checkout, so the commit is known there. The project link is the one URL with a scheme hermetic writes itself. It is a link, not a resource, so pages still load nothing from outside the output directory.

### Footer and header details
- Footer: 0.72rem, muted text, links in the link colour, "hermetic" linking to the project page, the commit in the code font.
- Header: the nav takes the rest of the header's row and the search button sits at its right end.
- Search dialog: an elevated background (`--elevated`: white in the light theme, a lighter grey than the page in the dark one), a stronger border and shadow, and the same backdrop.
- The "All results" link is the last option of the listbox, reached with the arrow keys like a result.
- The editor's save status ("Saved", "Saving…", "Not saved") moves out of the header to a small fixed label in the window's bottom-left corner, muted unless something is not saved. `browser-editing` only requires that the page shows the state, not where.

## Risks / Trade-offs

- [With the script on narrow screens, "All pages" is one step further away, behind the sidebar toggle] → `g p` reaches it directly, and the header's Journals and Graph links stay. Accepted, as asked.

- [Searching takes one more step: click, then type] → `/` and `Ctrl+K` open the dialog with the field focused, so keyboard users type straight away as before. Mouse users get a bigger field and more room for results.
- [Older browsers without `<dialog>` or `:modal`] → Every browser the site targets supports both. In any browser without them, the button would do nothing visible and `search.html` would still work. Accepted.
- [The live-reload index refresh while the dialog is open] → It already re-runs the query when the result list is visible. The dialog keeps that listener.
